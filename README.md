# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

Пользователь может включать и выключать отопление в доме удалённо.

**Мониторинг температуры:**

Система опрашивает датчики температуры и отображает пользователю актуальные данные в веб-интерфейсе.

### 2. Анализ архитектуры монолитного приложения

| Параметр                   | Описание                                                                        |
|----------------------------|---------------------------------------------------------------------------------|
| Язык программирования      | Go                                                                              |
| База данных                | PostgreSQL                                                                      |
| Архитектура                | Монолит                                                                         |
| Взаимодействие компонентов | Синхронное, прямое управление с сервера                                         |
| Масштабируемость           | Ограниченная: возможно только масштабирование всего приложения целиком          |

| Способ подключения         | Только через выезд специалиста, пользователь сам не может подключить устройство |

### 3. Определение доменов и границы контекстов

| Домен                    | Назначение и обоснование                                                                |
|--------------------------|-----------------------------------------------------------------------------------------|
| Device Management        | Управление жизненным циклом устройств: подключение, активация, отключение, статус.      |
| Heating Control          | Управление включением/выключением отопления, логика поддержания температуры.            |
| Monitoring (Telemetry)   | Получение и отображение температурных данных с сенсоров.                                |
| User Management          | Регистрация и аутентификация пользователей, привязка к устройствам и домам.             |
| SmartHome Control Center | Интерфейс пользователя для управления устройствами и просмотра текущего состояния дома. |

### **4. Проблемы монолитного решения**

- Все компоненты системы (управление отоплением, телеметрия) реализованы в одном модуле без явных границ и зон
  ответственности.
- Отсутствует возможность масштабировать только приём телеметрии или управление устройствами — масштабируется всё
  целиком.
- Любые изменения (например, бизнес-логика отопления) требуют полной пересборки и перезапуска всего приложения.
- Сбой любого модуля (например, получение телеметрии) может остановить всю систему.
- Отсутствие модульных границ усложняет тестирование отдельных частей.
- CI/CD не позволяет независимо выкатывать логику отопления, мониторинга — только целиком.

# Задание 4. Создание и документирование API

### 1. Тип API

#### Gateway — внешние клиенты

Используется HTTP/REST API по следующим причинам:
- REST является общепринятым стандартом для клиент-серверного взаимодействия.
- Поддерживается всеми внешними потребителями (веб-клиенты, мобильные приложения).
- Упрощает документирование и тестирование с использованием OpenAPI/Swagger.
- Удобен для реализации механизмов авторизации, аутентификации и контроля доступа.

#### Микросервис — микросервис 

Используется gRPC по следующим причинам:

- Более высокая производительность и меньшая нагрузка на сеть за счёт бинарной сериализации.
- Наличие строгих контрактов и автогенерации кода из .proto файлов.
- Поддержка двунаправленного стриминга.
- Удобство масштабирования и поддержки распределённых систем.

### 2. Документация API

OpenApi спецификация внутренних сервисов, генерируется на основе proto файлов, описывающих gRPC сервисы для каждого микросервиса.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе
   /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска
   postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
